# Performance Design — screenshot-editor（mvp）

performance-requirements.md（PERF-1〜4）を満たす技術的アプローチ。Python + PySide6 + Pillow を前提とする [tech-stack-decisions]。

## 設計方針

| 目標 | 設計アプローチ |
|------|--------------|
| PERF-1 プレビュー即時反映 | プレビューは**表示解像度に合わせた縮小画像**に対して加工を適用し表示する。原寸への適用は保存時のみ。スライダー連続操作は軽いデバウンス（例50〜100ms）で過剰再計算を抑える。 |
| PERF-2 開くのが速い | Pillowで開いてプレビュー用縮小版を一度生成しキャッシュ。原寸は保存時まで遅延ロード可。 |
| PERF-3 保存が速い | 原寸に EditSettings を1パスで適用し、Pillowで書き出し。非破壊アトミック（一時ファイル→リネーム）。 |
| PERF-4 バッチ | 各画像を順次 read→apply→save。**処理はワーカースレッド（QThread/QThreadPool）で実行**し、UIスレッドをブロックしない。進捗はシグナルでUIへ通知（AC2.1.4）。 |

## 並行実行のスレッド境界

- UIスレッド（PySide6）は core/io を**ワーカースレッド経由**で呼ぶ。core は純粋関数で状態を持たないためスレッド安全。
- 進捗・完了は Qt シグナル/スロットでUIスレッドへマーシャリング（Pillowイメージを直接UIへ渡さず、完了通知＋結果パスのみ）。
- 単体編集のプレビュー適用は縮小版のため軽量で、UIスレッドで同期実行しても目標内に収まる想定（重い場合はワーカーへ）。

## リソース

- メモリ: 原寸1枚＋縮小プレビューを保持。バッチは1枚ずつ処理しメモリ常駐を避ける。
- 高解像度/大量枚数はmvp主対象外だがクラッシュ回避（NFR1）。

## Assumptions & Open Questions

- デバウンス値・縮小サイズの具体値はコード生成で実測調整。
