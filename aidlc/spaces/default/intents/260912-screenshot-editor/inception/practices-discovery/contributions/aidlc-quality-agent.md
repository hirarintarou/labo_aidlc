## Contribution

品質エンジニアとして、リードドラフトのテスト方針・カバレッジ・CI 品質ゲート・テスト種別・インタビューで解消すべきギャップを独立にレビューした。

### テスト方針（Methodology + Ordering）

- **Methodology: test-after / Ordering の記述は本ツールの性質に妥当**。個人開発・GUI デスクトップアプリでは、実装後に対象レイヤーのテストを書く test-after が現実的で、org.md の既定とも一致する。ただし画像処理のコアロジック（補正・画質調整・フィルタ・入出力・非破壊保存）は**純粋関数／副作用の少ないモジュールとして UI から切り離せる部分**であり、この層に限っては「振る舞いを先に決めてからテストを書く」余地がある。混在させる場合は org.md の指針どおり `custom` を選ぶ余地があることを、統合ターンで意識してほしい（現状ドラフトは単一の test-after で問題ないが、後述のロードマップ次第）。
- **Ordering に「マージ前にローカルでスイートをグリーン確認」が含まれている点は良い**。CI 環境の有無に依存せず品質ゲートが成立する。

### 80% ラインカバレッジ下限の実現可能性（solo mvp）

- mvp スコープの 80% ライン下限は org.md 由来の既定だが、**アプリ全体（GUI 含む）に一律 80% を課すと個人開発では過大**になりやすい。GUI イベントハンドラ・描画・OS ダイアログ連携は単体テストのコストが高く、80% を満たすためだけの薄いテストは「Coverage は目標ではなくガイド」の原則に反する。
- **推奨する現実解**: カバレッジ下限を**コアの画像処理・入出力・保存ロジック層に限定して適用**し、UI/配線層は対象から除外（あるいは別基準）とする。この「測定対象スコープ」の切り分けをインタビューで確定すべき。切り分けが決まれば、solo でも 80% は無理なく達成できる。
- 下限を全体に対する数値として残すか、コア層に限定するかは**団体規約（org.md の mvp 80% 下限）と矛盾しない範囲での特化**として team.md に明記するのが望ましい。

### カバレッジツール・CI 品質ゲート

- 技術スタック未確定のためツール名保留は妥当。確定後の具体像として、想定される主要スタックごとに次を team.md の注記に残しておくと Code Generation が迷わない:
  - **.NET (C#/WPF/WinForms)**: `dotnet test` + coverlet + ReportGenerator
  - **Python (PySide/Tkinter + Pillow)**: pytest + pytest-cov + coverage.py
  - **JS/TS (Electron/Tauri)**: Vitest/Jest + c8/nyc
- **CI ゲートの現実解**: リモート CI（GitHub Actions 等）が無くても、**pre-commit / pre-push フックまたは単一の `make test`/タスクスクリプト**で「テスト green + カバレッジ下限」をローカルで機械的に強制する仕組みを 1 つ用意することを推奨。「手動でローカル実行」だけだと個人開発では確実にすり抜ける。CI 導入の有無はインタビュー項目（ドラフトの Open Uncertainty と一致）。

### 重視すべきテスト種別（この製品固有）

- **非破壊保存の不変条件テスト（最重要 / P0）**: 保存処理後に**元画像ファイルのバイト列・mtime が不変**であることをアサートする。加工結果は必ず別パスへ出力される。discovered-rules の `NEVER 元画像を上書き・破壊する` に 1:1 対応する回帰テストを必ず用意する。
- **PNG/JPEG ラウンドトリップテスト（P0）**: 読み込み→保存→再読み込みで、PNG は**画素完全一致（可逆）**、JPEG は**寸法・チャンネル・許容誤差内**を検証。加えて、入力形式と出力形式のクロス（PNG→JPEG、JPEG→PNG）も 1 ケースずつ。
- **画像処理ロジックの単体テスト（P0〜P1）**: 補正・画質調整・フィルタ・トリミング/リサイズ・クレジット付与。恒等操作（変化量ゼロ）や境界（1px、極端なサイズ、アルファ有無、EXIF 回転）を含める。
- **プロパティベーステスト（推奨）**: 「PNG round-trip は恒等」「リサイズ後の寸法＝指定値」など、少数の性質を fast-check/Hypothesis 等で回すと、少ないテスト数で solo でもエッジケースを広くカバーできる（mvp との相性が良い）。
- **E2E は最小限**: GUI 全体の E2E は 1〜2 本（画像を開く→加工→非破壊保存の疎通）に留め、pyramid の ice cream cone を避ける。walking skeleton の「入出力＋非破壊保存の最小疎通を早期確認」（team-practices）と、この疎通 E2E を**同一の検証**として結びつけると重複が減る。

### テストデータ戦略

- 小さな**フィクスチャ画像**（数 px の PNG/JPEG、アルファ有無、EXIF 回転付き 1 枚）をリポジトリに固定同梱。バイナリ肥大を避けるため合成生成（テスト内でプログラム的に作る）を優先し、実写スクショは最小限にする。

### インタビューで解消すべきギャップ（quality 観点）

1. **カバレッジ下限の測定対象スコープ**: 80% をアプリ全体に課すか、コア層（画像処理・入出力・保存）に限定するか。← solo での実現可能性を左右する最重要論点。
2. **CI の形態**: リモート CI（GitHub Actions）を用意するか、pre-push フック／ローカルタスクで下限を強制するか、完全手動か。
3. **JPEG ラウンドトリップの許容誤差基準**（非可逆のためピクセル完全一致は不可能）。
4. **非破壊保存の出力先・命名規則**（既定の保存先、サフィックス等）— テスト対象として明確化が必要（discovered-rules の Open Questions とも重複）。
5. **プロパティベーステストを標準ツールセットに含めるか**（solo の労力対効果として）。

## Positions

- AGREE: Testing Posture の Methodology=test-after と Ordering の明示 — 個人開発・GUI アプリの性質に合致し、org.md 既定とも整合する。
- AGREE: 非破壊保存・PNG/JPEG ラウンドトリップを重点テストとする方針 — 製品のコア不変条件であり discovered-rules と 1:1 で対応する。
- OBJECT: 80% ラインカバレッジ下限をアプリ全体に暗黙適用している点 — GUI/配線層を含めた一律 80% は solo mvp では過大かつ形骸化しやすく、測定対象スコープ（コア層限定など）をインタビューで確定しないと実現可能性が不明。
- OBJECT: 品質ゲートが「マージ前にローカルで手動実行」に留まる点 — 個人開発では手動確認はすり抜けやすく、pre-commit/pre-push フックか単一タスクでテスト green＋カバレッジ下限を機械的に強制する仕組みの要否をインタビューで決めるべき。
