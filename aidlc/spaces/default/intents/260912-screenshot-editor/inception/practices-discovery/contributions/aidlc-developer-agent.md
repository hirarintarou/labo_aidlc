## Contribution

リードドラフトの5セクションは個人・ローカル完結・mvp の文脈に沿って妥当に調整されている。開発者観点（命名・レイヤー境界・エラー処理・ファイル構成・コードスタイル）で、スタック非依存の原則と、スタック確定時に決める項目を以下に補う。

### レイヤー境界（画像処理コア と UI の分離）
- ドラフトの Code Style / Testing Posture は「画像処理ロジックの単体テスト中心」に言及しているが、そのテスト容易性を担保する**構造上の境界**が team-practices に明文化されていない。ここは mvp でも譲れない設計原則なので、Code Style（もしくは Way of Working）に一文加えるべき。
  - **画像処理コアは UI フレームワークに依存させない**。補正・画質調整・フィルタ・トリミング/リサイズ・クレジット付与・入出力は、GUI（ウィンドウ・ボタン・ダイアログ）を一切 import しない純粋なモジュール群として実装し、UI 層はコアを呼び出すだけにする。
  - この境界により、GUI を起動せずコアの単体テストが可能になり、ドラフトが掲げる「非破壊保存」「PNG/JPEG ラウンドトリップ」の重点テストが現実的になる。
  - 依存方向は一方向（UI → コア → I/O）とし、コアから UI を参照しない。スタックが未確定でも、この依存規則は言語非依存で成立する。
- 推奨する論理レイヤー（言語非依存）: `ui`（画面・入力）/ `core` または `imaging`（画像変換ロジック）/ `io`（読み込み・非破壊書き出し・フォーマット判定）。物理的なパッケージ/フォルダ名は言語イディオムに委ねてよいが、**この3責務の分離**は原則として固定する。

### エラー処理（破損画像・非対応フォーマット）
- discovered-rules に「非破壊で保存する」「PNG/JPEG 入出力をサポート」はあるが、**入力が想定外だったときの振る舞い**が team-practices / discovered-rules いずれにも規定されていない。デスクトップツールの品質を左右する箇所なので、原則を明記すべき。
  - **入力境界（ファイル読み込み・フォーマット判定）で早期に検証し、失敗を握りつぶさない**（fail fast）。破損ファイル・0バイト・非対応拡張子・拡張子と実体の不一致は、コア処理へ渡す前に弾く。
  - **利用者に届くエラーは技術例外そのものではなく、日本語で理由が分かるメッセージに変換する**（例:「このファイルは開けませんでした（対応形式は PNG / JPEG です）」）。UI 層でユーザー向け表現へマッピングし、コア層はドメイン固有の型付きエラーを投げる責務分担にする。
  - **1枚の失敗でツールを落とさない**。1人利用のツールでも、想定外入力でクラッシュせず操作を継続できることを非機能的な最低ラインとする。
  - 非破壊保存との整合: **保存処理は「元画像を読めた」ことと「出力先が書ける」ことを検証してから書き出す**。途中失敗で中途半端な出力を残さない（可能なら一時ファイル→リネームのアトミック書き出し）。この原則は言語非依存で、Forbidden の「元画像を上書き・破壊しない」を実装レベルで補強する。

### 命名・ファイル構成
- 「プロジェクト全体のリネーム規則は設けず言語イディオムに従う」は個人開発として妥当。追加すべきは**構造の一貫性**であって命名表記ではない。
  - ファイルは**技術レイヤーではなく機能/責務でまとめる**方針を推奨（コアの各操作＝補正・フィルタ・トリミング等を機能単位で配置）。ただし上記のレイヤー境界（ui/core/io）は跨がない。
  - テストファイルは対象ソースに隣接、または言語慣習のミラー配置とする（ドラフトの「隣接テスト」慣行と整合）。スタック確定時に配置規約を1行で記録する。

### スタック確定時に決めること（保留の明示）
- フォーマッタ/リンタの具体名（ドラフト通り保留で妥当）。
- 画像処理ライブラリの選定と、それがコア層に閉じ込められること（アダプタ的に薄くラップし、`io`/`core` の外へライブラリ型を漏らさない）。
- 型付きエラーの実現手段（例外型 / 結果型など、言語の慣習に従う）。

これらは「スタック非依存の原則」＝レイヤー境界・fail fast・非破壊アトミック書き出し・機能単位構成 を先に固定し、具体名だけをスタック確定時に埋める形にすれば、mvp の負荷を増やさずに設計品質を担保できる。

## Positions

- AGREE: リネーム規則を設けず言語イディオムに従う方針 — 個人開発では表記統一より構造の一貫性が重要で、ドラフトの判断は妥当。
- AGREE: リンタ/フォーマッタ具体名の保留とスタック確定時記録 — スタック未確定下での過度な先取りを避ける健全な判断。
- OBJECT: team-practices に画像処理コアと UI の**レイヤー境界**が明文化されていない — 「画像処理ロジックの単体テスト中心」を成立させる前提条件であり、mvp でも固定すべき原則。
- OBJECT: 破損画像・非対応フォーマット時の**エラー処理原則**が team-practices / discovered-rules いずれにも無い — 早期検証・ユーザー向けメッセージ変換・クラッシュ回避・アトミック書き出しは非破壊保存要件を実装で担保するために不可欠。
