## Contribution

セキュリティ観点でリードドラフトをレビューした。前提はローカル完結・オフライン・Windows 専用・個人開発・非破壊保存・ネットワーク I/O なし・秘密情報や個人情報の収集なし、である。この前提を尊重し、比例原則に沿って「本当に効くもの」と「このスコープでは過剰なもの」を切り分けて記す。

### 本当に効くもの（このスコープで採用を推奨）

1. **依存ライブラリの出所と固定（最重要）**
   - 本ツールは画像処理ライブラリに依存する。ローカル完結でネットワーク I/O が無くても、**サプライチェーンは唯一の実質的な攻撃面**である。悪意あるパッケージやタイポスクワッティングは、ビルド時・実行時に開発機（=利用者の PC）でコードを実行しうる。
   - ALWAYS 依存を**正確なバージョンで固定（ピン留め）**し、ロックファイル（例: `package-lock.json` / `poetry.lock` / `Cargo.lock` / `requirements.txt` のハッシュ付き）をリポジトリにコミットする。
   - 画像処理ライブラリは**広く使われ・活発に保守されている実績のあるもの**を選ぶ（例の傾向: ImageSharp / System.Drawing 代替、Pillow、image クレート等 — スタック確定時に確定）。導入時にパッケージ名のタイプミス／類似名（タイポスクワッティング）を必ず目視確認する。
   - 依存の追加・更新は**最小限**に保ち、不要な推移的依存を持ち込まない。

2. **未検証の画像ファイルの安全な取り扱い（実質的リスク）**
   - 入力画像は「外部から来た未検証データ」として扱う。個人ツールでも、他者から受領した／ネットで拾ったスクリーンショットを開くと、**細工された画像による画像パーサの脆弱性（メモリ破壊・DoS・過大メモリ確保）**を踏みうる。これは STRIDE の Tampering / Denial of Service に相当する。
   - ALWAYS 画像デコードは選定した画像処理ライブラリの標準 API を用い、**独自のパーサを書かない**（Secure by default / 車輪の再発明をしない）。
   - 破損・巨大・想定外フォーマットの入力に対し、**クラッシュせずエラーとして扱う**（サイズ・寸法の妥当性チェック、例外の握り）。ラウンドトリップ・非破壊保存のテストに、破損入力・巨大寸法の異常系を1〜2件含めることを推奨（quality の担当領域と重なるが、セキュリティ動機として明記）。
   - 出力の**非破壊保存**は integrity 保護そのものであり、リードの discovered-rules（元画像を上書きしない）を強く支持する。パス組み立て時のディレクトリトラバーサル（`..` を含む出力名）や既存ファイル上書きの取り扱いに注意する。

3. **軽量なリンタ/フォーマッタとローカル秘密スキャン**
   - リンタは選定言語の**セキュリティ系ルール**（例: ESLint security plugin / Bandit / Clippy 等）を有効化する。これは追加コストが小さく、危険な API 使用の早期検知に効く（shift-left）。リードの Code Style（言語標準のリンタ/フォーマッタをルートに設定）方針に上乗せする位置づけ。
   - 本ツール自体は秘密情報を持たない想定だが、リポジトリへの誤コミット防止として**軽量な secret スキャン（例: gitleaks の pre-commit）**を任意で入れる価値はある。コストが低く、将来 API キー等を扱う変更が入っても保険になる。

### このスコープでは過剰（採用しない／Open Question 止まりで良い）

- **DAST / 動的スキャン**: 稼働中のサーバやエンドポイントが無いため対象外。適用不可。
- **SAST の重量級ツール（SonarQube 等）や CI 常設のセキュリティゲート**: ネットワーク面・認証・認可・サーバ側ロジックが無いため費用対効果が低い。リンタのセキュリティルールで十分。CI 自体をローカル実行のみにするか否かは、リードの evidence にある Open Question のままで妥当。
- **認証/認可・暗号化・監査ログ・レート制限・WAF・KMS 等**: 単一利用者のローカルデスクトップアプリで、ネットワーク越しのアクセスも秘密情報も無いため不要。OWASP Top 10 の大半（アクセス制御・注入・SSRF 等）はサーバ/Web 前提であり本ツールに該当しない。
- **コンテナイメージスキャン・IaC スキャン**: コンテナも IaC も無いため適用外。
- **SBOM の常設運用**: ロックファイルのコミットで供給網の透明性は実務上十分。フォーマルな SBOM 生成は個人 mvp には過剰。

### discovered-rules への追記提案（インタビューで確認のうえ確定）

- ALWAYS 依存ライブラリを正確なバージョンで固定し、ロックファイルをコミットする。
- ALWAYS 入力画像を未検証データとして扱い、標準ライブラリの API でデコードし、破損・異常入力でクラッシュさせない。

## Positions

- AGREE: 非破壊保存とローカル完結を Mandated/Forbidden とした discovered-rules — 唯一実質的な integrity・情報保護の制約を正しく硬い制約に格上げしており、セキュリティ観点でも中核。
- AGREE: staging/production・CD パイプライン・本番承認ゲートを適用外とした Deployment 方針 — ネットワーク面が無いスコープに対し過剰なゲートを避けており比例的で妥当。
- OBJECT: 依存ライブラリの出所・バージョン固定・未検証画像の安全な取り扱いが team-practices / discovered-rules のいずれにも明示されていない — ネットワーク I/O が無い本ツールで唯一実質的な攻撃面（サプライチェーンと画像パーサ）であり、少なくとも Code Style の補足かインタビュー項目として明示すべき。
