# Team Practices

> 本プロジェクトは個人開発（開発者=利用者=本人、1人）・Windows 専用・ローカル完結の
> 小規模ツールである。以下は `org.md` の既定プラクティスを個人・ローカル完結・mvp
> スコープに合わせて調整し、インタビュー（Q1〜Q8）と 3 つのサポートレビュー
> （quality / developer / devsecops）を統合して確定したものである。

## Way of Working

- 単一リポジトリでの **trunk-based development** を採用する。すべての作業は短命の
  作業ブランチを経て `main` にマージする（Q1=A）。個人開発のため、形式的な PR
  レビューは省略し、セルフ確認とローカルでの動作確認で品質を担保する。
- Construction のワークツリーはベースブランチ・マージ先ともに `main` とする。
- Bolt ブランチは `main` へ **squash-merge** し、`main` の履歴を Bolt 単位で
  リニアに保つ。
- 環境の分離（staging / production）は行わない。ローカル完結のデスクトップアプリ
  であり、トランクは 1 本のまま維持する。
- コミットメッセージはワークスペース規約に従い **日本語** で記述する。

## Walking Skeleton

- **walking skeleton を作る**（Q2=B、`skeleton: on` 相当）。機能を作り込む前に、
  「画像を開く → 加工 → 非破壊で保存」が端から端まで通る最小の骨組みを最初に用意し、
  各部品（入出力・画像処理コア・UI・保存）が実際につながることを確かめてから、
  個別機能（補正・画質調整・フィルタ・トリミング/リサイズ・クレジット付与）を足す。
- 最初の Bolt でこの縦断スライスを通す。PNG/JPEG の入出力と非破壊保存の疎通を
  骨組みの一部として早期に確認する。この最小疎通は Testing Posture の E2E
  最小疎通（画像を開く→加工→非破壊保存）と同一の検証として結びつけ、重複を避ける。

## Testing Posture

- **Methodology**: test-after
- **Ordering**: テスト対象となる各レイヤー（画像処理コア・入出力・保存を優先）を
  実装し、その直後に当該レイヤーのテストを記述・実行し、`main` へのマージ前に
  ローカルでスイート全体がグリーンであることを確認する。
- カバレッジ（測定対象スコープを特化、Q4=A）: **80% のラインカバレッジ下限を、
  画像処理の中核ロジック層（補正・フィルタ・入出力・保存）に限定して適用する**。
  GUI / 配線層（画面・イベントハンドラ・OS ダイアログ連携）は下限の対象外とする。
  これは `org.md` の mvp 80% 下限を、solo mvp で実現可能な測定対象スコープに
  特化させたものであり、団体規約と矛盾しない範囲での特化として本 team.md に明記する。
- テスト種別: 画像処理ロジック（補正・画質調整・フィルタ・トリミング/リサイズ・
  クレジット付与・入出力）の単体テストを中心とする。非破壊保存（元画像のバイト列・
  mtime が不変であること）と PNG/JPEG のラウンドトリップ（PNG は画素完全一致、
  JPEG は寸法・チャンネル・許容誤差内、PNG↔JPEG のクロスも各 1 ケース）を
  最重点（P0）でテストする。恒等操作・境界（1px、極端なサイズ、アルファ有無、
  EXIF 回転）や、破損・巨大・非対応入力の異常系（1〜2 件）を含める。GUI 全体の
  E2E は最小限（1〜2 本、Walking Skeleton の疎通と共用）に留める。
- CI ゲート（Q5=A）: リモート CI は必須としない。**pre-commit / pre-push フック
  （または単一のタスクスクリプト）で「テスト green ＋ カバレッジ下限」をローカルで
  機械的に強制する仕組みを 1 つ用意する**。手動のローカル実行のみには依存しない
  （個人開発ではすり抜けやすいため）。
- ツール: 技術スタック未確定のため、選定した言語・フレームワークの標準的な
  テストランナーとカバレッジ計測ツールに従う（例: .NET は `dotnet test`＋coverlet、
  Python は pytest＋pytest-cov、JS/TS は Vitest/Jest＋c8/nyc）。確定時に
  プロジェクト設定へ記録する。

## Deployment

- 「ステージング/本番パイプライン」ではなく、**ローカルビルド/インストール** を
  デプロイと見なす（Q6=A）。ローカル完結・Windows 専用・個人利用のデスクトップ
  アプリであり、リモート環境・CD パイプライン・本番承認ゲートは適用外とする。
- リリースは自分向けのローカルビルド成果物（実行可能ファイル/インストーラ）の
  生成をもって完了とする。バージョンはタグで管理してよい。
- 複数環境の昇格は行わない。

## Code Style

- 言語のイディオムに従う。技術スタック未確定のため、フォーマッタ・リンタは選定した
  言語の標準（例: Prettier/Black/gofmt 等、対応するリンタ）をリポジトリルートに
  設定し、確定時に記録する。リンタにはセキュリティ系ルール（例: ESLint security
  plugin / Bandit / Clippy 等）を有効化する。
- リンタが既にカバーするルールは重複して規定しない。フレームワークによる
  コードスタイル提案は、リンタ設定で未カバーの場合にのみ適用する。
- 個人開発のためプロジェクト全体のリネーム規則は設けない。命名は言語のイディオム
  （camelCase / snake_case 等）に従う。表記統一より **構造の一貫性** を重視し、
  ファイルは技術レイヤーではなく機能/責務でまとめる。テストは対象ソースに隣接
  （または言語慣習のミラー配置）とする。
- **レイヤー境界（Q7 採用）**: 画像処理コアは UI フレームワークに依存させない。
  依存方向は一方向（**ui → core → io**）とし、コア（補正・画質調整・フィルタ・
  トリミング/リサイズ・クレジット付与・入出力ロジック）は GUI（ウィンドウ・ボタン・
  ダイアログ）を一切 import しない純粋なモジュール群として実装する。論理レイヤーは
  `ui`（画面・入力）/ `core`（画像変換ロジック）/ `io`（読み込み・非破壊書き出し・
  フォーマット判定）の 3 責務に分離する（物理的なフォルダ名は言語イディオムに委ねる）。
  画像処理ライブラリは `core`/`io` の内側に薄くラップし、ライブラリ型を外へ漏らさない。
- **エラー処理（Q7 採用）**: 入力境界（ファイル読み込み・フォーマット判定）で早期に
  検証し、失敗を握りつぶさない（fail fast）。破損ファイル・0 バイト・非対応拡張子・
  拡張子と実体の不一致は、コア処理へ渡す前に弾く。利用者に届くエラーは技術例外そのもの
  ではなく、日本語で理由が分かるメッセージに変換する（例:「このファイルは開けません
  でした（対応形式は PNG / JPEG です）」）。1 枚の失敗でツールを落とさない。

## Assumptions & Open Questions

- 技術スタック（言語・GUI フレームワーク・画像処理ライブラリ）が未確定のため、
  テストランナー・カバレッジツール・フォーマッタ・リンタ・pre-commit/pre-push
  フックの具体名はスタック確定後に記録する。
- JPEG ラウンドトリップの許容誤差基準（非可逆のため画素完全一致は不可能）を
  スタック確定時に定める。
- 非破壊保存の既定の出力先・命名規則（サフィックス等）は後続ステージで確定する。
- プロパティベーステスト（PNG round-trip 恒等・リサイズ後寸法一致など）を標準
  ツールセットに含めるかは、solo の労力対効果を見て判断する（推奨だが必須ではない）。
