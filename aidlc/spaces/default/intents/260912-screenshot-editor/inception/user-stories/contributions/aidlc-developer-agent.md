## Contribution

実装可能性・サイジング・ui→core→io へのマッピング・依存順序の観点でドラフトをレビューした。全体として要件と素直に対応しており solo mvp として妥当な粒度。以下、実装者視点の指摘。

### 1. 欠落している技術ストーリー（walking skeleton）— 最重要

team-practices は `skeleton: on`（Q2=B）で「画像を開く → 加工 → 非破壊で保存が端から端まで通る最小の骨組みを最初の Bolt で通す」ことを明示し、これを Testing Posture の E2E 最小疎通と同一視すると規定している。しかし stories.md には縦断スライスを表す技術ストーリーが存在せず、Dependencies も機能ストーリー間の依存だけを並べている。実装着手時に「まず何を通すか」がストーリーとして落ちていない。次のストーリー追加を推奨する:

- **US0.1 縦断スライス（open → no-op → 非破壊保存）を通す — Must**（US1.x 群より前段の最初の Bolt）。AC 例: 「PNG/JPEG を開く → 恒等（無加工）→ 元と同じフォルダに接尾辞付きで保存、元画像バイト列不変」が ui→core→io を実際に貫通し、E2E 1 本＋ラウンドトリップ（PNG 画素完全一致 / JPEG 許容誤差内）が green。US1.1 と US1.7 の疎通面を先取りするが、team-practices の指示どおり重複テストは骨組みと共用する。

これが無いと「各機能ストーリーを積む前に配線を検証する」という確定済みプラクティスがバックログに反映されない。

### 2. サイジング

- **US1.2 基本補正 / US1.3 画質調整** は AC が 3 本ずつだが、いずれも「1 スライダ → core 変換 1 関数 → プレビュー反映」で構造が同一のため、まとめて 1 ストーリーで妥当。過分割ではない。
- **US1.5 トリミング・リサイズ** は実装様相が異なる 2 機能（トリミングは矩形選択 UI＋クロップ、リサイズは寸法指定＋補間）を 1 ストーリーに同居させている。core 側は別関数、ui 側も操作系が別。solo mvp で許容範囲だが、着手時に US1.5a/US1.5b へ割るとサイジングと進捗把握が楽になる（提案、必須ではない）。
- **US1.6 クレジット付与** は AC2 本で妥当。ただし FR6.2 の「不透明度」と FR6.4 のガイドライン目的が AC に落ちていない（後述）。
- **US2.1 バッチ** は「設定の再利用＋反復適用＋部分失敗継続＋集計表示」を含み、単体編集ストーリーより一段重いが、AC が 3 本に分かれており実装単位として追える。分割不要。

### 3. AC の具体性と ui→core→io マッピング

依存方向 ui→core→io を検証可能にするには、「プレビューに反映される」だけでなく core が純粋関数として何を返すかが AC に必要。中核 80% カバレッジは core/io に課されるため、AC は core レイヤーで検証できる形が望ましい。

- **US1.2/US1.3/US1.4**: AC が「プレビューに反映される」（ui 観測）に寄っている。core の観点（例「同一入力に同一パラメータで決定的な出力画像を返す」「恒等パラメータで入力と一致」）を 1 行足すと、GUI 抜きで単体テスト可能になり Testing Posture（core 中心の単体テスト）と整合する。
- **US1.5.2 リサイズ**: 「指定寸法になる」は良い（core で寸法一致を assert 可能）。アスペクト比保持の有無が未定義 — 実装分岐に効くので明記推奨。
- **US1.6**: 不透明度（FR6.2）が AC に無い。また「core が画像へテキストを合成した結果を返す」形にしておくと検証しやすい。
- **US1.7.4**（中途半端な出力を残さない）は fail-fast/安全保存プラクティスの核。AC は良いが「一時ファイル→リネーム」という io の実装契約に触れており、io レイヤーのストーリーとして明確でよい。
- 巨大/破損入力の異常系（NFR1, team-practices の P0 テスト）は US1.1.2 と US2.1.2 でカバーされているが、「1 枚の失敗でツールを落とさない」は io/core 境界の検証点として妥当。

### 4. 依存順序の現実性

- 記載の依存（US1.2〜US1.6 は US1.1 依存、US1.7 は加工系の後段、US2.1 は US1.x 依存）は実装順として現実的。
- ただし US0.1（骨組み）を先頭に置くと、US1.1 と US1.7 は骨組みで疎通済みの面を厚くする形になり、依存グラフがより実態に合う。
- US2.1 は「1 枚で決めた設定」を前提とするため、加工設定を保持・再適用する仕組み（設定オブジェクトの表現）が core 側に要る。これは US1.x に暗黙依存する設計上の前提であり、機能設計で設定モデルを固める必要がある旨をどこかに残すとよい（今ストーリーで解決不要）。

### 5. 軽微

- MVP マイルストーンのストーリー列挙（US1.1・US1.2・US1.5・US1.6・US1.7＋US1.4）は requirements の受け入れ目安と一致しており良い。US1.3（画質調整）が最初の目安から外れている点は requirements 準拠で問題なし。

## Positions

- AGREE: ワークフロー別 2 グループ構成、各加工機能の個別ストーリー化、MoSCoW 付与、依存関係の大枠、requirements との対応は実装観点で妥当。
- OBJECT: walking skeleton（`skeleton: on`）に対応する縦断スライスの技術ストーリー（open→no-op→非破壊保存の end-to-end 疎通、US0.1 相当）が欠落している。確定済みプラクティスがバックログに反映されていないため追加を要する。
- OBJECT: US1.2/US1.3/US1.4 の AC が ui 観測（プレビュー反映）に寄っており、中核 80% カバレッジを負う core レイヤーで単体検証できる観点（決定的出力・恒等一致等）が AC に欠けている。ui→core→io 分離を AC 段階で検証可能にするため補強を要する。
